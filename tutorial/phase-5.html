05

Context Management & Turn Snapshots

💡
How to use this lesson: You already have a working agent loop from Phase 4. This phase is a small change in one file — src/harness/loop.ts — but it teaches a big harness idea: what you log and what you send to the model are not the same thing. Type each snippet; use the sidebar line guides as before.

Phase 4 gave you repetition: the model can call tools many times per user message. Phase 5 gives you visibility: before every model call, you freeze a small record of harness state so you can answer questions like “which tools were available on step 3?” or “was the working directory already changed?”

Production harnesses (Pi, OpenCode, Hermes) all separate durable session logs from provider context. You started that split in Phase 4 with toApiMessages(), which strips timestamp. Here you extend it: some messages exist only for humans and debugging — they never go back to Grok.

Two channels (memorize this):
  • Durable log — everything in sessions/<id>.jsonl: user, assistant, tool results, timestamps, turn snapshots.
  • Model context — only what toApiMessages() returns when you call agent.chat(). Must match what the API accepts and what you intend the model to reason over.

If you dump debug JSON into the log but forget to filter it out of model context, you waste tokens and confuse the model. If you filter it out but never log it, you cannot debug flaky runs. Phase 5 does both correctly.

Why turn snapshots?

One user turn (what you type at the CLI) can include many loop steps (model call → tools → model call → …). Between those steps, your harness changes state: tool results append to history, and later you might change cwd, tool lists, or permissions (Phase 6).

A turn snapshot is a harness-owned message that records “what the world looked like right before this model call.” Research harness docs call this pattern out explicitly: snapshot at turn boundaries so mid-turn mutations do not create impossible-to-reproduce bugs.

You are not building Pi’s full snapshot (model ID, stream options, extension hooks). You are learning the shape of the idea with four fields any beginner can understand.

Prerequisites: Finish Phase 4 first — loop.ts with toApiMessages, runTurn, and main.ts running via npm start. This phase only edits loop.ts (and optionally documents hidden on Message in session.ts).

Step 1: Exclude hidden messages from model context

Phase 4’s toApiMessages() already removed the hidden field from each message. That is not enough: a snapshot is still a system message with a long JSON body. You need to drop entire messages marked hidden: true before calling the API.

In src/harness/loop.ts, replace your existing toApiMessages function with this version:

src/harness/loop.ts — toApiMessages() (updated)
/** Strip harness-only messages and fields before sending history to the API. */
export function toApiMessages(messages: Message[]): Record<string, unknown>[] {
  return messages
    .filter((m) => !m.hidden)
    .map(({ timestamp, hidden, ...rest }) => rest);
}

Filter, then strip

Order matters: remove whole messages first, then peel metadata off survivors.

Line 1Comment documents intent

Future you (and teammates) should know this function is the single gate for “what Grok sees.” Compaction, summarization, and profile-specific prompts also belong here in advanced harnesses.

Lines 2–5filter + map

.filter((m) => !m.hidden) drops turn snapshots and any other harness-only rows. .map(...) then removes timestamp and hidden from messages that do go to the API.

Why: Snapshots belong in the JSONL audit trail, not in the model’s reasoning context.

Optional clarity in src/harness/session.ts — add hidden?: boolean; to the Message type next to timestamp. Your [key: string]: any index signature already allows it; the explicit field helps TypeScript autocomplete.

Step 2: Define what a snapshot contains

Still in loop.ts, add a type and a helper below toApiMessages and above runTurn. This keeps snapshot logic in one place.

src/harness/loop.ts — TurnSnapshot type & recordTurnSnapshot()
type TurnSnapshot = {
  step: number;
  messageCount: number;
  toolsAvailable: string[];
  workingDir: string;
  timestamp: string;
};

async function recordTurnSnapshot(session: Session, step: number): Promise<void> {
  const snapshot: TurnSnapshot = {
    step,
    messageCount: session.getHistory().length,
    toolsAvailable: TOOLS.map((t) => t.function.name),
    workingDir: process.cwd(),
    timestamp: new Date().toISOString(),
  };

  await session.addMessage(
    'system',
    `TURN SNAPSHOT: ${JSON.stringify(snapshot)}`,
    { hidden: true },
  );
}

Freeze state before each model call

Each field answers a common debugging question.

Lines 1–7TurnSnapshot fields
  • step — which iteration of the for loop (0, 1, 2…). Maps to “model call #N this user turn.”
  • messageCount — how many rows are in session history before this call. Grows as tools append results.
  • toolsAvailable — names from your TOOLS array. If the model never calls read_file, you can check whether it was even offered.
  • workingDir — process.cwd() at snapshot time. Relative paths in tool args depend on this.
  • timestamp — when the snapshot was taken (separate from per-message timestamp on other rows).
Lines 9–16Build the object

TOOLS.map((t) => t.function.name) assumes OpenAI-style tool schemas from Phase 3 — same shape you already pass to chat().

Lines 18–22Persist with hidden: true

role: 'system' keeps snapshots out of the user/assistant narrative but easy to grep. Prefix TURN SNAPSHOT: so you can search JSONL files. JSON.stringify(snapshot) stores one line of compact JSON inside content.

Why: addMessage is your durability hook — snapshots survive crashes the same way user messages do.

Step 3: Call the snapshot at the top of each loop step

Inside runTurn, find the for loop from Phase 4. Add one line as the first statement in the loop body — immediately after for (let step = 0; …) { and before const response = await agent.chat(…).

src/harness/loop.ts — inside runTurn's for loop
  for (let step = 0; step < MAX_ITERATIONS; step++) {
    await recordTurnSnapshot(session, step);

    const response = await agent.chat(
      toApiMessages(session.getHistory()),
      TOOLS,
    );

Snapshot → then chat

Never call the model before you record what the harness looked like.

Lines 1–2Order of operations

When step 0 runs, history usually ends with the user message you appended at the start of runTurn. When step 1 runs, history includes assistant tool-call rows and tool results from step 0 — messageCount in the snapshot reflects that growth.

Why: If you logged after chat(), you would mix “state before the call” with “state after the model already replied.”
Lines 4–7Unchanged chat call

toApiMessages(session.getHistory()) now automatically excludes every snapshot you just appended, because they carry hidden: true.

Step 5: What lands in the JSONL file

Run a short task, then open sessions/<your-session-id>.jsonl. You should see snapshot lines mixed with normal messages. Example (pretty-printed for reading; the file stores one JSON object per line):

sessions/example.jsonl — excerpt

{"role":"assistant","content":"","timestamp":"2026-06-02T12:00:02.000Z","tool_calls":[...]}

Read the story backward

When something looks wrong, find the snapshot for that step first.

Line 1User row

Normal durable message — always sent to the model (not hidden).

Line 2step 0 snapshot

messageCount: 1 — only the user message so far. toolsAvailable lists all three file tools. This row is not in Grok’s context thanks to hidden: true + toApiMessages filter.

Line 4step 1 snapshot

messageCount jumped — assistant tool call + tool result were appended between steps. Compare snapshots side-by-side to see history growth per model call.

Step 6: Verify it works

From the project root:

Terminal — run and inspect
npm start

# After a task that used at least one tool, in another terminal:
grep "TURN SNAPSHOT" sessions/*.jsonl | head -5
Type check (no API call)
npx tsc --noEmit

Success criteria

The agent should behave like Phase 4; only the log gets richer.

npm startBehavior unchanged

Try: “List every file in src/harness.” You should still see tool → list_files and a final answer. Optional step N → model lines appear if you added Step 4.

grepSnapshots on disk

At least one line per model step. Multi-tool turns produce multiple snapshots with increasing step and messageCount.

tscTroubleshooting
  • Property 'hidden' does not exist — add hidden?: boolean to Message in session.ts, or rely on the index signature.
  • Snapshots in model replies / weird answers — you forgot .filter((m) => !m.hidden) in toApiMessages.
  • No snapshots in file — recordTurnSnapshot is not awaited, or it sits after chat() instead of before.
What you are not building yet (on purpose):
  • Compaction / summarization — trimming old tool output before it fills the context window (Phase 08 teaser).
  • Permission profiles — different tool sets per mode (Phase 6). Snapshots will later show which profile was active.
  • UI that hides snapshot rows — hidden is ready for a TUI or web UI in Phase 7.
When should you stop and test?
  • After Step 1: npx tsc --noEmit — quick type check.
  • After Step 3: npm start with a multi-step task, then grep TURN SNAPSHOT on the session file.
  • After Phase 6: Same CLI; profiles will change which tools run — snapshots help prove what was allowed each step.
Checkpoint: You now practice context governance in miniature: rich durable logs, lean model context, and a per-step snapshot of harness state. That trio is what separates a toy chat script from a harness you can debug. Phase 6 adds permission profiles so the harness — not the model — decides which tools are allowed.
