07

Observability & Iteration

💡
How to use this lesson: Phases 1–6 gave you memory, tools, a loop, snapshots, and profiles. Phase 7 adds the harness eyes — structured logs you can read while the agent runs and after it fails. You will create logger.ts, thread a HarnessLogger through loop.ts and main.ts, and learn a simple iterate-from-logs workflow.

Until now, debugging meant squinting at scattered console.log lines and opening sessions/*.jsonl. That works once, but it does not scale. When a turn fails — max iterations, permission denial, mystery tool loop — you need answers fast:

  • How many model steps did this user message take?
  • Which tools ran, for how long, and did any get denied?
  • How many tokens did each model call cost?
  • Did the turn end cleanly or throw?

Observability means the harness records those facts in a consistent shape. Iteration means you change prompts, tools, or profiles based on evidence — not vibes.

Two logs, two jobs (keep both):
  • sessions/<id>.jsonl (Phase 1) — conversation the model sees (plus hidden snapshots). For replaying chat history.
  • logs/<id>.jsonl (this phase) — harness events only. For performance, cost, and debugging harness behavior.

Do not stuff harness metrics into chat messages. Phase 5 taught you to keep model context lean; observability stays on the side.

Prerequisites: Phase 6 complete — profiles, getToolSchemas, permission denials from executeTool. Your main.ts should use profile.systemPrompt (not a leftover hard-coded SYSTEM_PROMPT from Phase 4).

Step 2: Create src/harness/logger.ts

A tiny structured event logger: one JSON object per line, human-readable prefix in the terminal, same pattern as session JSONL.

src/harness/logger.ts — preview helper & class
import fs from 'fs/promises';
import path from 'path';

/** Shorten tool results for logs — avoid dumping whole files. */
export function preview(text: string, max = 120): string {
  const oneLine = text.replace(/\s+/g, ' ').trim();
  return oneLine.length <= max ? oneLine : `${oneLine.slice(0, max)}…`;
}

export class HarnessLogger {
  private readonly logPath: string;

  constructor(sessionId: string) {
    this.logPath = path.join(process.cwd(), 'logs', `${sessionId}.jsonl`);
  }

  async event(kind: string, fields: Record<string, unknown> = {}): Promise<void> {
    const record = {
      ts: new Date().toISOString(),
      kind,
      ...fields,
    };

    console.log(this.formatConsole(record));
    await fs.mkdir(path.dirname(this.logPath), { recursive: true });
    await fs.appendFile(this.logPath, JSON.stringify(record) + '\n');
  }

  private formatConsole(record: Record<string, unknown>): string {
    const { ts, kind, ...rest } = record;
    const parts = Object.entries(rest).map(
      ([key, value]) => `${key}=${typeof value === 'string' ? value : JSON.stringify(value)}`,
    );
    return `[harness] ${kind}${parts.length ? ' ' + parts.join(' ') : ''}`;
  }
}

One event API

Call logger.event('tool', { … }) everywhere you care about.

Lines 1–6preview()

Tool results can be huge (entire source files). Logs store a preview only. Full content stays in sessions/ for the model.

Lines 8–12Constructor

One log file per session ID — easy to correlate with sessions/<same-id>.jsonl.

Lines 14–22event()

kind is a short string you will grep later (model_step, tool, turn_end). fields holds numbers and strings — keep values JSON-serializable.

Why structured: Production harnesses export to OpenTelemetry or Datadog; JSONL is the beginner-friendly version of the same idea.
Lines 24–30formatConsole

Terminal lines look like [harness] tool step=1 name=read_file durationMs=12 denied=false — scannable while the agent runs.

src/main.ts — full while loop body (Phase 4 REPL + Phase 7 logging)
  while (true) {
    const line = await rl.question('> ');
    if (!line.trim()) break;

    console.log('\n… agent working …\n');

    const turnStarted = Date.now();

    await logger.event('turn_start', {
      profileId: profile.id,
      inputChars: line.length,
    });

    try {
      const reply = await runTurn(session, agent, line, profile, logger);

      await logger.event('turn_end', {
        profileId: profile.id,
        durationMs: Date.now() - turnStarted,
        status: 'ok',
        replyChars: reply.length,
      });

      console.log(`\n${reply}\n`);
    } catch (err) {
      const message = err instanceof Error ? err.message : String(err);

      await logger.event('turn_error', {
        profileId: profile.id,
        durationMs: Date.now() - turnStarted,
        status: 'error',
        message,
      });

      console.error(err);
    }
  }

TroubleshootingCommon issues
  • No logs/ folder — no turn completed yet, or logger not passed into runTurn.
  • Expected 5 arguments — update runTurn(session, agent, line, profile, logger) at the call site.
  • usage always undefined — provider may omit usage; fields stay optional. Loop still works.
  • Duplicate turn_end — expected (loop + main); filter by presence of durationMs vs loopSteps.

Step 7: Iterate from logs (the harness engineering loop)

When something goes wrong, use this checklist before blaming the model:

  1. Reproduce once — same profile, same prompt. Note session ID.
  2. Open logs/<id>.jsonl — find the last turn_error or the final model_step before the run stopped.
  3. Classify the failure
    • High toolCallCount every step → tool loop; tighten prompts or lower MAX_ITERATIONS.
    • denied: true → profile mismatch; fix profile or user expectation.
    • Rising totalTokens → context bloat; Phase 8 compaction teaser.
    • Slow durationMs on tools → filesystem or huge reads; trim tool output later.
  4. Change one harness knob — tool description, profile allow-list, system prompt, sandbox — run again.
  5. Compare logs — did loopSteps or token totals improve?

Addy Osmani’s harness engineering point applies here: recurring mistakes are harness problems. Logs tell you which ratchet to add next.
