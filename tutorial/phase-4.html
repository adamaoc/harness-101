04

The Agent Loop

💡
How to use this lesson: Same pattern as earlier phases — type each snippet, use the sidebar, expand one section at a time. You already have durable sessions (Phase 1), a Grok client (Phase 2), and file tools (Phase 3). This phase wires them into a repeating loop — the moment your project stops being a chat wrapper and becomes an agent.

This is the heart of the harness. A single chat() call can return one tool request — but real tasks need many rounds: list a folder, read a file, think, edit, verify. The loop handles that automatically.

Basic loop flow (one user prompt):
  1. Append the user's message to the session
  2. Send current conversation history + tool schemas to the model
  3. If the model requests tools → run them, append results to history, go to step 2
  4. If the model replies with text → save it and return that answer to the user

You'll create two files:

  • src/harness/loop.ts — the loop logic (runTurn)
  • src/main.ts — a small CLI so you can type tasks in the terminal

Step 1: Create src/harness/loop.ts

Start with imports and a safety constant. The loop will call your existing pieces — it does not replace them.

src/harness/loop.ts — imports & guard
import type { Message } from './session.js';
import type { Session } from './session.js';
import type { GrokAgent } from './agent.js';
import { TOOLS, executeTool } from './tools.js';

const MAX_ITERATIONS = 25;

Pull in what you built

The loop orchestrates — it doesn't reimplement tools or API calls.

Lines 1–3Type-only imports

import type tells TypeScript these imports are erased at runtime — you only need them for typing. With verbatimModuleSyntax, that's required for type-only symbols.

Line 4TOOLS & executeTool

Same exports from Phase 3. Every model call passes TOOLS; every tool request goes through executeTool.

Line 6MAX_ITERATIONS

A runaway model could call tools forever. This cap stops infinite loops and gives you a clear error. Production harnesses often add smarter stopping rules; 25 is plenty for learning.

Why: Harness problems include "stuck in a loop" — always bound iteration count early.

Step 2: Strip harness metadata before API calls

Your Session stores extra fields like timestamp (and later hidden for turn snapshots in Phase 5). The Grok API only accepts standard chat roles — send a cleaned copy of history.

src/harness/loop.ts — toApiMessages()
/** Strip harness-only fields before sending history to the API. */
export function toApiMessages(messages: Message[]): Record<string, unknown>[] {
  return messages.map(({ timestamp, hidden, ...rest }) => rest);
}

Context transform (minimal version)

Real harnesses filter, trim, or summarize here. Yours just drops local metadata.

Line 1export function toApiMessages

Exported so you can unit-test it later. The loop and only the loop should decide what the model sees — not random callers reaching into session.messages.

Lines 2–3Destructuring rest

{ timestamp, hidden, ...rest } peels off harness fields; rest keeps role, content, tool_calls, tool_call_id, etc. — whatever the API needs for that message.

Why: Durable logs can be richer than model context. Phase 5 adds more of this pattern.

Step 3: runTurn — start the loop

We build runTurn in three pieces (Steps 3, 4, and 5) — all in the same file, all inside one for loop. This step adds the function signature, saves the user message, and opens the loop with the first model call.

Add the block below after toApiMessages() from Step 2. Stop at the end of this snippet — do not close the for loop or runTurn yet.

src/harness/loop.ts — runTurn (part 1 of 3; loop body continues in Steps 4–5)
/**
 * Run one user turn: append the user message, loop with the model until
 * it returns a final text answer (possibly after several tool rounds).
 */
export async function runTurn(
  session: Session,
  agent: GrokAgent,
  userInput: string,
): Promise<string> {
  await session.addMessage('user', userInput);

  for (let step = 0; step < MAX_ITERATIONS; step++) {
    const response = await agent.chat(
      toApiMessages(session.getHistory()),
      TOOLS,
    );
    const message = response.choices[0]?.message;

    if (!message) {
      throw new Error('Model returned no message');
    }

One turn, many model calls

Part 1 of runTurn. The for loop stays open at the end of this snippet.

Lines 5–9runTurn parameters

session — durable memory. agent — Grok client. userInput — what the human typed this turn. Returns the final assistant text when the model stops calling tools.

Line 10Save user message first

Always persist before calling the model. If the process crashes mid-turn, you still have the user's request on disk.

Lines 12–16Call the model

getHistory() then toApiMessages() — full conversation so far, cleaned. TOOLS tells Grok what it can invoke. This is the same chat() from Phase 2, now inside a loop.

Lines 17–21Read the response

choices[0]?.message — optional chaining because TypeScript's noUncheckedIndexedAccess treats array access as possibly undefined. We throw if the API returned nothing useful.

Step 4: Handle tool calls — the "act" half of the loop

Where this goes: Still in runTurn, still inside the for loop from Step 3. Paste the block below immediately after the if (!message) { throw … } block — same indentation (four spaces). Do not start a new function or a new loop.

When message.tool_calls is non-empty, the model wants your harness to do work. Save the assistant message (including the tool call objects), run each tool, append tool results, and continue the loop without returning yet.

src/harness/loop.ts — paste inside runTurn's for loop, after Step 3
    const toolCalls = message.tool_calls ?? [];

    if (toolCalls.length > 0) {
      await session.addMessage('assistant', message.content ?? '', {
        tool_calls: toolCalls,
      });

      for (const toolCall of toolCalls) {
        if (toolCall.type !== 'function') continue;
        const fn = toolCall.function;
        console.log(`  tool → ${fn.name}`);
        const result = await executeTool(fn.name, fn.arguments);
        await session.addMessage('tool', result, {
          tool_call_id: toolCall.id,
          name: fn.name,
        });
      }
      continue;
    }

Observe → decide → act → observe

Part 2 of runTurn — same for loop, pasted after the if (!message) check.

Line 1tool_calls ?? []

Some responses omit tool_calls entirely. Default to an empty array so the rest of the code can always use .length.

Lines 3–6Save assistant + tool_calls

The API requires the assistant message that requested tools to stay in history, with the full tool_calls array attached. content may be empty when the model only wants tools — that's normal.

Why: If you only save tool results without the assistant tool-call message, the next API request fails validation.
Lines 8–16Execute each tool

if (toolCall.type !== 'function') continue — the OpenAI SDK types allow custom tool call shapes; our harness only implements named functions from TOOLS. Skip anything else.

toolCall.function has name and arguments (a JSON string). executeTool from Phase 3 parses and runs it. The tool message needs tool_call_id matching the call id so the model knows which result belongs to which request.

console.log is optional but helpful — you'll see the agent working in the terminal before the final answer.

Line 17continue

Jump back to the top of the for loop — send updated history to the model again. The model now "sees" the tool output and decides what to do next (more tools or a final reply).

Step 5: Finish when the model replies with text

Where this goes: Immediately after the tool if block from Step 4 — same indentation, still inside the for loop. When the model did not request tools, execution skips the if (toolCalls.length > 0) block and runs these lines instead.

This step also closes the for loop and runTurn with the final } braces. After this snippet, runTurn is complete.

src/harness/loop.ts — paste after Step 4; closes the for loop and runTurn
    const text = message.content ?? '';
    await session.addMessage('assistant', text);
    return text;
  }

  throw new Error(`Agent loop exceeded ${MAX_ITERATIONS} iterations`);
}

Done for this user prompt

Returning ends runTurn; the CLI prints the string.

Lines 1–3Final assistant message

Persist the answer to JSONL like every other message. return text bubbles up to main.ts for display.

Line 6Exceeded iterations

If the loop ran 25 times without a plain-text finish, something is wrong (model stuck retrying, bad tool errors, etc.). Throw so the CLI can show an error instead of hanging silently.

Recap — your loop.ts file

You should now have a complete src/harness/loop.ts with two exports:

  • toApiMessages() — strips harness-only fields (timestamp, hidden) before history goes to Grok.
  • runTurn() — runs one user prompt end-to-end.

runTurn saves the user's message, then repeats until the model stops calling tools:

  1. Send session history + TOOLS to agent.chat().
  2. If the model requests tools → save the assistant message, run executeTool for each call, append tool results to the session, and loop again.
  3. If the model replies with plain text → save that assistant message and return the text to whoever called runTurn.

Every message (user, assistant, tool) is written to the session as you go, so the next chat() call sees the full story — including tool output the model needs to finish the task. If the loop runs 25 times without a text answer, it throws instead of spinning forever.

That's the agent loop: the harness talks to Grok, runs your file tools when asked, and hands back the model's final reply. Next you'll wire a CLI so you can type prompts from the terminal.

Step 6: Create src/main.ts — the CLI entry point

Wire session load, a system prompt, and a readline loop. This is how you actually talk to the agent — no HTTP server, just Node in the terminal.

src/main.ts
import readline from 'readline/promises';
import { stdin as input, stdout as output } from 'process';
import { GrokAgent } from './harness/agent.js';
import { Session } from './harness/session.js';
import { runTurn } from './harness/loop.js';

const SYSTEM_PROMPT =
  'You are a helpful coding agent working in a local TypeScript project. ' +
  'Use list_files and read_file to explore before editing. ' +
  'When you finish a task, reply with a concise summary for the user.';

async function main() {
  const session = new Session();
  await session.load();
  const agent = new GrokAgent();

  if (session.getHistory().length === 0) {
    await session.addMessage('system', SYSTEM_PROMPT);
  }

  console.log(`Session ${session.id} — empty line to quit\n`);

  const rl = readline.createInterface({ input, output });

  while (true) {
    const line = await rl.question('> ');
    if (!line.trim()) break;

    console.log('\n… agent working …\n');
    try {
      const reply = await runTurn(session, agent, line);
      console.log(`\n${reply}\n`);
    } catch (err) {
      console.error(err);
    }
  }

  rl.close();
}

main().catch(console.error);

Minimal REPL

Read–eval–print loop: prompt, run agent, print reply, repeat.

Lines 1–2readline

Node's built-in line reader — no extra npm package. readline/promises gives await rl.question() instead of callbacks.

Lines 7–10SYSTEM_PROMPT

Sets expectations: explore before edit, summarize when done. Stored as a normal system message so it persists in JSONL with the session.

Why: The harness shapes behavior through system context, not just tool descriptions.
Lines 12–15Session + agent setup

load() resumes prior messages if the JSONL file exists. New sessions get a fresh UUID and an empty history until you add the system prompt.

Lines 17–19System message once

Only when history is empty — avoids duplicating the system prompt every time you restart the CLI on the same session file.

Lines 23–35Prompt loop

Each non-empty line runs one full runTurn (which may include many model calls). Empty line exits. try/catch keeps the REPL alive if one turn throws (API error, max iterations, etc.).

TroubleshootingCommon issues
  • 401 / auth errors — check .env and XAI_API_KEY.
  • Tool error in output — the loop is working; the model hit a bad path. Read the tool result in the JSONL file.
  • Max iterations — model may be looping on a failing tool; fix the underlying error or raise the cap temporarily while debugging.
When should you stop and test?
  • After typing loop.ts: Run npx tsc --noEmit if you want a quick type check — no API call yet.
  • After main.ts (here): Run npm start — this is the milestone. You should see tool calls in the terminal and a final answer.
  • After Phase 5: Same CLI; you'll add turn snapshots inside the loop before each chat() call.
