Implementing Tools

💡
How to use this lesson: Same pattern as Phases 01–02 — type each snippet, use the sidebar, expand one section at a time. You already wired tools into GrokAgent.chat() in Phase 2; this phase defines what those tools are and how your harness runs them when the model asks.

Tools are how your agent actually does work in the real world. Without them, Grok can only talk. With them, it can read, write, and explore files in your project — the same primitives every coding agent needs.

We start with three essential tools: read_file, write_file, and list_files. Each tool has two halves:

  • Schema — a JSON description you send to the model so it knows the tool name, what it does, and what arguments to pass.
  • Handler — TypeScript code you run on disk when the model requests that tool. The model never touches your filesystem directly; your harness does.

Quality rule (worth repeating)

Always require the agent to read a file before editing it. Say that in the tool description. Models that skip reading tend to hallucinate file contents and overwrite good code. Your descriptions are part of the harness.

Step 1: Create src/harness/tools.ts

This file exports two things the agent loop will use in Phase 4: TOOLS (schemas for chat()) and executeTool() (run a tool by name). We also add a small workspace sandbox so paths cannot escape your project folder.

src/harness/tools.ts — imports & path safety
import fs from 'fs/promises';
import path from 'path';

const WORKSPACE_ROOT = process.cwd();

function resolvePath(relativePath: string): string {
  const resolved = path.resolve(WORKSPACE_ROOT, relativePath);
  if (!resolved.startsWith(WORKSPACE_ROOT)) {
    throw new Error(`Path escapes workspace: ${relativePath}`);
  }
  return resolved;
}

Workspace sandbox

Every file tool goes through resolvePath.

Lines 1–2Node filesystem imports

Same modules as session.ts — async file I/O and cross-platform paths.

Line 4WORKSPACE_ROOT

process.cwd() is the folder you run the agent from (your project root). All relative paths are interpreted from here — same as running ls in the terminal from that directory.

Why: Later phases can change this to a specific repo path; for now, "where you started the process" is enough.
Lines 6–11resolvePath()

path.resolve turns ../secrets into an absolute path. We then check it still starts with WORKSPACE_ROOT. If someone tricks the model into ../../.env, we throw instead of leaking files outside the project.

Why: Phase 6 adds richer permissions; this is the first safety layer.

Step 2: Tool schemas for the model

Add the TOOLS array below your resolvePath function. This is the OpenAI/Grok shape: each entry is type: 'function' plus a function object with name, description, and parameters (JSON Schema).

In Phase 4 you'll pass TOOLS into agent.chat(messages, TOOLS). The model reads these descriptions when deciding whether to call a tool.

src/harness/tools.ts — TOOLS array
export const TOOLS = [
  {
    type: 'function' as const,
    function: {
      name: 'read_file',
      description:
        'Read the full text content of a file. Use this before editing a file you have not read in this conversation.',
      parameters: {
        type: 'object',
        properties: {
          path: {
            type: 'string',
            description: 'File path relative to the project root (e.g. src/harness/session.ts)',
          },
        },
        required: ['path'],
      },
    },
  },
  {
    type: 'function' as const,
    function: {
      name: 'write_file',
      description:
        'Write text to a file, creating parent folders if needed. Prefer reading the file first so you know what you are changing.',
      parameters: {
        type: 'object',
        properties: {
          path: { type: 'string', description: 'Relative path from project root' },
          content: { type: 'string', description: 'Full new file contents' },
        },
        required: ['path', 'content'],
      },
    },
  },
  {
    type: 'function' as const,
    function: {
      name: 'list_files',
      description: 'List files and folders in a directory (one level). Use to explore before reading.',
      parameters: {
        type: 'object',
        properties: {
          path: {
            type: 'string',
            description: 'Directory relative to project root (use "." for root)',
          },
        },
        required: ['path'],
      },
    },
  },
];

What the model sees

Descriptions are prompts — write them for the model, not for humans skimming code.

Line 1export const TOOLS

One array, imported by the loop and passed wholesale to chat(). Keeping schemas in one place makes it easy to add tools later.

Line 3type: 'function' as const

The API expects the literal 'function'. as const narrows the type so TypeScript matches the SDK without widening to string.

Lines 5–18read_file schema

name must match the case in executeTool later. description tells the model when to use the tool — we explicitly say "before editing." parameters is JSON Schema: one required string path.

Lines 22–36write_file schema

Two required fields: path and content (full file body, not a patch). Real agents often add a separate search_replace tool later; for learning, full writes are simpler.

Lines 40–54list_files schema

Lets the model explore without guessing paths. "." means the project root. We only list one directory level — deep trees come in advanced patterns (Phase 8).

Step 3: Handlers — the harness "hands"

Below TOOLS, add private async functions that do the real work. They take plain strings (already validated paths from resolvePath) and return text the model will read as the tool result.

src/harness/tools.ts — handlers
async function readFile(pathArg: string): Promise<string> {
  const filePath = resolvePath(pathArg);
  return await fs.readFile(filePath, 'utf-8');
}

async function writeFile(pathArg: string, content: string): Promise<string> {
  const filePath = resolvePath(pathArg);
  await fs.mkdir(path.dirname(filePath), { recursive: true });
  await fs.writeFile(filePath, content, 'utf-8');
  return `Wrote ${pathArg} (${content.length} characters)`;
}

async function listFiles(pathArg: string): Promise<string> {
  const dirPath = resolvePath(pathArg);
  const entries = await fs.readdir(dirPath, { withFileTypes: true });
  const lines = entries.map((e) => (e.isDirectory() ? `${e.name}/` : e.name));
  return lines.join('\n') || '(empty directory)';
}

Real filesystem I/O

Return strings — the model only sees text tool results.

Lines 1–4readFile

Resolves the path, reads UTF-8 text, returns the whole file. Large files can blow up context — trimming or paging belongs in later phases.

Lines 6–10writeFile

mkdir(..., { recursive: true }) creates missing folders (e.g. src/new/). Returns a short confirmation string, not the file body — enough for the model to know it succeeded.

Lines 12–16listFiles

withFileTypes: true tells us folder vs file so we can suffix folders with /. One entry per line keeps the result easy for the model to scan.

Step 4: executeTool — dispatch by name

When the model calls a tool, the API gives you a tool call id, a function name, and an arguments string (JSON). Your loop will pass that arguments string here. This function parses JSON, routes to the right handler, and catches errors so the model gets a useful message instead of a crashed process.

src/harness/tools.ts — executeTool
export async function executeTool(name: string, argsJson: string): Promise<string> {
  let args: Record<string, unknown>;
  try {
    args = JSON.parse(argsJson);
  } catch {
    return `Invalid tool arguments JSON: ${argsJson}`;
  }

  try {
    switch (name) {
      case 'read_file':
        return await readFile(String(args.path ?? ''));
      case 'write_file':
        return await writeFile(String(args.path ?? ''), String(args.content ?? ''));
      case 'list_files':
        return await listFiles(String(args.path ?? '.'));
      default:
        return `Unknown tool: ${name}`;
    }
  } catch (err) {
    const message = err instanceof Error ? err.message : String(err);
    return `Tool error (${name}): ${message}`;
  }
}

Bridge from API to handlers

Phase 4 calls this once per tool request from the model.

Line 1export async function executeTool

Public entry point. name matches function.name in the schema. argsJson is the raw string from tool_calls[].function.arguments — not a parsed object yet.

Lines 2–7Parse arguments

Models occasionally emit malformed JSON. Returning an error string (instead of throwing) lets the model retry on the next loop iteration.

Lines 9–18switch (name)

Each case must match a name in TOOLS. String(args.path ?? '') coerces unknown JSON shapes to strings safely. list_files defaults path to '.' if missing.

Lines 19–22catch (err)

Missing files, permission errors, and sandbox violations become tool results like Tool error (read_file): ENOENT... so the agent loop keeps running.

Why: Tool failures are normal; the model should read the error and adjust, not crash your process.

Step 5 (optional): Smoke-test your tools

You do not have an agent loop yet, so the model cannot call these tools end-to-end. You can still verify the handlers work by calling executeTool yourself from a tiny script.

First install tsx — a small runner that executes TypeScript with ESM imports (including the .js extensions our nodenext setup requires):

Terminal
npm install -D tsx

Why tsx?

Plain ts-node often fails on ESM projects with "type": "module".

Line 1npm install -D tsx

Adds tsx as a dev dependency. We'll use it here and again in Phase 4 to run the agent CLI. You only install once.

Why not ts-node alone: Our imports use ./harness/tools.js (correct for Node ESM). tsx resolves that to your .ts files at run time; bare npx ts-node often cannot.

Create src/smoke-tools.ts at the project root level under src/ (not inside harness/):

src/smoke-tools.ts
import { executeTool } from './harness/tools.js';

async function main() {
  console.log(await executeTool('list_files', JSON.stringify({ path: 'src/harness' })));
  console.log(await executeTool('write_file', JSON.stringify({ path: 'scratch.txt', content: 'hello from harness' })));
  console.log(await executeTool('read_file', JSON.stringify({ path: 'scratch.txt' })));
}

main().catch(console.error);
Terminal (from project root)
npx tsx src/smoke-tools.ts

Quick manual check

Not automated tests — just proof your hands work.

Line 1.js extension in import

With "module": "nodenext", Node expects the emitted file extension in imports. If your editor complains, match whatever Phase 1's tsconfig uses — the goal is a successful run from the project root.

Lines 3–7Three tool calls

Lists your harness folder, writes scratch.txt, reads it back. Delete scratch.txt afterward if you like — or add it to .gitignore.

Terminalnpx tsx

Run from the same folder as package.json. You should see a directory listing, a write confirmation, then hello from harness. No API key needed for this step.

Alternatively: npm run smoke-tools if you add "smoke-tools": "tsx src/smoke-tools.ts" to the scripts section of package.json.

When should you stop and test?
  • After Phase 3 (here): Optional smoke test above — confirms file tools only. You still cannot "talk to the agent" in a loop.
  • After Phase 4: This is the real milestone. You'll add loop.ts and a small CLI entry point (src/main.ts). That is when you run the harness, type a task, and watch Grok call read_file / list_files over multiple turns. No separate HTTP server — you run it like any Node script from the terminal.
  • Phases 5–7: Keep using the same CLI; each phase improves memory, safety, and logging.

If the smoke test passes but you are eager to see the model use tools — finish Phase 4 first. Wiring TOOLS into one chat() call without a loop only produces a single tool request with no follow-up.

Checkpoint: You have TOOLS and executeTool. GrokAgent.chat() already accepts a tools array from Phase 2. Next, Phase 4 connects session history, model responses, and tool execution into a repeating loop — that's when your harness becomes an agent.
